# Keyboard release on configuration changes: offline prototype

Updated 2026-11-09. This is own Thumb source and an offline proof, **not an
installable firmware candidate**. No device, updater, loader or physical NVM
was accessed. The published no-wait/OL2/OL3 files and hashes are unchanged.
The independent recovery/current-backup gate in [RECOVERY.md](RECOVERY.md)
still applies.

## Problem and explicit policy

The stock release dispatcher uses the button's **current** assignment. Replacing
usage27 with usage28 or a DPI action while27 is held can therefore leave27 in
the mouse's keyboard buffer. This happens on the ordinary middle-button control
as well as the no-wait screen button; it was not introduced by the OLED NOP.

The prototype chooses a small, explicit policy: **a stock profile load or a
successful button-table replacement ends this mouse's virtual keyboard keys**.
This includes reloading the same profile, and temporarily loading a different
profile during a legacy settings transaction. An unrelated primary keyboard
is not accessed; this source only clears the mouse's own firmware buffer.

This means a held virtual key is released at the configuration operation,
before physical release. It stays released until another physical press.
Applications should release mouse buttons before reading/replacing legacy
profiles as well as before applying bindings. OL3 status and pixel requests
do not load a profile, so they do not cause this release policy.

## Exact new code, separate from OL3

Source: [g9_keyboard_release_prototype.S](../firmware/g9_keyboard_release_prototype.S).
Built with clang's ARMv5T/Thumb assembler, with no external relocations.

| Item | Value |
|---|---|
| Prototype placement used only in emulated memory | `0x47680` |
| Prototype size |108 bytes, 128 bytes with 32-byte framing alignment |
| Prototype code SHA256 | `953eb2ffee52866397055640851b32e030f1cce388b847791f4777d6e9fb1f0f` |
| Published OL3 code, unchanged |636 bytes, SHA256 `f9938ccff010dd680f1df37c0b0a97a3a6af6c8aeb12859475ca4dc19eba85ed` |
| Combined padded code footprint |768 of the previously bounded 1152 append bytes |

The extra code fits after the existing 640-byte OL3 padded payload without
increasing the existing aligned updater transfer ceiling. This is a placement
proof, **not** evidence that a combined container, boot image or updater is ready.
No new raw firmware resource, package or installer is generated by the proof.

| Original call site | Old bytes | New emulated bytes | New target and original callee replay |
|---|---|---|---|
| `0x30D80`, end of profile loader | `06 f0 92 fb` | `16 f0 7e fc` | `0x47680`, replays logger `0x374A8` |
| `0x33F4E`, accepted SET08 table copy | `f1 f7 25 f8` | `13 f0 9d fb` | `0x4768C`, replays ROM memcpy `0x24F9C` with original arguments |

Both hooks are after the stock function prologue and return to the original
continuation. The profile hook is after both the checksum-valid and default
button-table copy branches. The SET08 hook is reached only after successful
checksum validation. The helper:

- Clears exactly `0x400B42..0x400B49`, the eight-byte range used by the stock
  keyboard reset, including modifier and all usage slots.
- Cancels ordinary and shortcut FSM states `0x400B2B` and `0x400B2C`, so a pending
  phase cannot later reinsert a key from the old assignment.
- If the old keyboard buffer, either FSM, or the keyboard dirty flag was active,
  leaves an empty report pending through `0x400AF6=1` and re-arms existing
  scheduler request bytes `0x400B19/0x400B1A=1`. Stock consumers of these request
  bytes include `0x35D98/0x35DB0` and `0x38C32`. It does not clear endpoint-ready.
- Leaves idle loads idle: no new keyboard report is requested when those states
  were all empty. It uses no allocated/global RAM and calls no boot/flash helper.

The wrappers preserve the original callee's effects and caller continuation.
The release helper additionally preserves r0-r4; inherited callee checks and the
direct helper fixture verify r0-r7 and stack canaries. Flags are scratch at these
call sites. The broad stock reset at `0x317FE` is deliberately not called: it
also clears other HID state and clears dirty rather than delivering key-up.

## Reproducible proof and limits

Run in WSL from the project directory:

```sh
tools/pyenv/bin/python tools/emulate_keyboard_release_prototype.py
```

The current fixture asserts 36 cases: 28 successful cases, six expected stock
failure reproductions used as controls, and two remaining short-tap failure
reproductions with the prototype enabled. Output is
`evidence/keyboard-release-prototype.json`; own object/layout are under `bin/`.
Vendor inputs, these binary build outputs and local evidence are not published.

The profile cases use the actual SET0C, main worker and profile-loader
instructions with synthetic global/profile flash records. The SET08 cases use
the actual dispatcher, checksum and copy paths. Button/ordinary FSM and USB
report assembly also execute as real Thumb instructions. Hardware FIFO/send,
display, ROM memcpy/zero-fill and persistence boundaries remain explicit stubs.
Debounced edges and endpoint readiness are supplied, not measured. There is no
real-time, OS, full RF/receiver, bootloader or firmware-startup emulation.

Coverage includes same/new/DPI assignments, same-profile reload, two held mapped
keys plus modifier, queued ordinary/shortcut cancellation, an empty release
retained while EP is busy, repeated taps, five idle profile loads and a rejected
SET08. Exact RAM-write allowlists and surrounding canaries bound the helper's
effects. Actual original callees and arguments are checked at both hooks.
The existing OL3 status and first pixel page run alongside the prototype and
preserve a held keyboard key without calling the profile loader.

The fixture invalidates Unicorn's translated-code cache after applying emulated
hooks: profile initialization has already executed the original loader, so a
plain `mem_write` alone can otherwise execute its cached original call. The
passing tests require recorded execution of the new code, not merely new bytes
visible in memory.

**Remaining gaps are intentional and still block a broad correctness claim:**

- A complete short tap can still disappear if release arrives before the first
  keyboard report is accepted. This prototype adds no queue or down/up delivery
  state. Both middle and screen controls continue to reproduce that limitation.
- A running macro can write keyboard data again after this helper; cancelling
  ordinary/shortcut state is not proof of macro cancellation or release safety.
- Mouse/consumer outputs, first key after MCU sleep, disconnect/reconnect,
  actual RF delivery, physical boot compatibility, input latency during OLED
  writes and custom frame lifetime remain outside this proof.
- Legacy read/profile reload now intentionally releases held virtual keys. That
  behavior must be reviewed before integrating a future combined candidate.

The next firmware step is an independent review of this policy and coverage,
then a separate bounded down/up-delivery design. No published OL3 marker/hash
should be silently reused for a changed installable image. Only after a new
fully reconstructed container and independent recovery are established can a
physical test plan be considered; none is requested now.
