# G9 PRO OLED: подтверждённые примитивы и проект протокола

Статус: **реальный Thumb-1 uploader с офлайн-проверкой**, исходник
`firmware/g9_oled.S`. Скомпилированный ARM-код исполняется в Unicorn вместе с
нативными обработчиками версии и отрисовки дисплея. Он ещё не проверен на
физической мыши; USB-команды для изображений ей не отправлялись. Наличие
предпросмотра в HUB не означает поддержку загрузки штатной прошивкой. Патч
обычной клавиши «0» — отдельное изменение из двух байтов.

Текущий минимальный протокол — **OL2**, wired-only, одна самодостаточная
страница на команду. Проверка поддержки использует существующий GET `0x0B`
длиной 8 байт. В нём отсутствуют ownership, framebuffer и сохранение в flash;
штатный renderer может перезаписывать картинку. Прежний Python reference v1
остаётся исследовательским тестом, его COMMIT/RESTORE не поддерживаются OL2.

Исследован официальный образ G9 PRO BT Ver1.08 Upgrade 20251028. SHA256 ресурса
до удаления проверочных слов:

```text
f7c4db8ffae37d033cbde4d670d70f32bd9ea62b36d0e6d7ba9cba5ce7d9efcc
```

Адреса ниже относятся к нормализованному образу с базой `0x28790`. Первые
16 байт — заголовок обновления, ARM-векторы начинаются с `0x287A0`.
Сторонний полный образ прошивки не включается в публичный исходный проект.

## Геометрия и расположение пикселей

| Параметр | Доказательство / значение |
|---|---|
| Логическая ширина штатного рендера | **120 колонок**: `OLED_Clear` пишет `0x78` байт на страницу; текст переносится после x=119 |
| Организация штатного рендера | **4 страницы по 8 бит**, 120 байт на страницу, **480 байт** на четыре страницы |
| Глубина | **1 бит на пиксель**, оттенков серого и RGB в этом тракте нет |
| Программируемая высота вывода | **28 строк**: последовательность инициализации содержит `A8 1B`, то есть multiplex ratio 27+1 |
| Рабочий размер предпросмотра | **120×28**, упаковочный буфер 120×32; четыре неиспользуемых бита последней страницы обнулять |
| Протокол дисплея | Команды, совместимые с семейством SSD13xx; точная модель кристалла по этим данным не установлена |
| Адрес шины | I²C 7-bit `0x3C`, передаваемый адрес записи `0x78` |
| Разделение команд/данных | Control byte `0x00` для команды, `0x40` для данных |

Размер 120×28 основан на рендере и настройке multiplex. Физическая ориентация
матрицы и соответствие последних четырёх бит видимым строкам ещё требуют
контрольного рисунка на реальном устройстве. Инициализация задаёт `A1`, `C0`,
`D3 2E`; поэтому нельзя обещать отсутствие отражения/смещения только по
офлайн-предпросмотру. Штатный рендер обращается к четырём страницам; полная
геометрия внутренней RAM контроллера этим не установлена. Это также не означает,
что существует отдельный готовый framebuffer в RAM MCU.

Для предложенного формата хоста используется обычная страничная упаковка:

```text
offset(x,y) = (y >> 3) * 120 + x
mask(x,y)   = 1 << (y & 7)
x = 0..119, y = 0..27
```

То есть бит 0 — первая логическая строка страницы. Последняя страница содержит
данные для y=24..27, её старшая тетрада равна нулю. Это явный контракт нового
API, который ещё предстоит сверить с физическим контрольным изображением.

Полная штатная последовательность инициализации, таблица `0x4654D`:

```text
AE 00 10 40 B0 81 30 A1 C0 A4 A6 A8 1B AD 40
D3 2E D5 41 D9 04 DA 10 DB 30 8D 52
```

После неё функция отдельно отправляет `AF` — display on.

## Подтверждённые функции исходной прошивки

| Адрес | Назначение и аргументы |
|---|---|
| `0x3CDDE` | Инициализация дисплея: 27 команд из `0x4654D`, затем `AF` |
| `0x3CDBE` | Отправка одной команды; `r0=command` |
| `0x3CEBE` | Установка позиции: `r0=x`, `r1=page`; отправляет `B0+page`, `10+(x>>4)`, `x&0F` |
| `0x3CEE6` | Запись блока: `r0=x`, `r1=page`, `r2=count`, `r3=pointer`; после позиционирования передаёт `78 40` и count байт |
| `0x3D7F0` | Заполнение блока одинаковым байтом: x, page, count, value |
| `0x3D824` | Очистка: четыре страницы, x=0, count=120, value=0 |
| `0x3CD7A` | Вывод одного байта на I²C |
| `0x3CDAE`, `0x3CD6A` | Начало/окончание транзакции шины |
| `0x3DAFA` | Выключение: команды `AE 8D 10` |
| `0x3DAE4` | Включение charge pump/display: `8D 72 AF` |

В Unicorn исполнен сам `0x3CEE6`: для каждой страницы получается ровно
`B0+page, 10, 00`, затем `78, 40` и 120 исходных байт. ROM, I²C и задержки
заменены сохранением аргументов; физическая передача не утверждается.

## RAM и взаимодействие со штатным экраном

Подтверждённые существующие переменные:

| Адрес | Использование |
|---|---|
| `0x400AF1` | Ожидание жеста удержания экранной кнопки; именно он мешает обычной «0» |
| `0x400AF2` | Флаг выключенного OLED: при значении 1 штатный код вызывает выключение или временно включает дисплей для перерисовки |
| `0x400B01` | Поглощение события при завершении специального жеста; не framebuffer |
| `0x400F88` | Контекст текущего HID-запроса: report id и указатель на данные |
| `0x400F91…` | Существующий буфер USB-запроса, используется также штатными настройками |
| `0x400DF0…` | Общий временный буфер протокола/настроек; не свободная память |
| `0x4010AE…` | Данные текущего макроса; не свободная память |

**Не размещать** постоянный framebuffer в этих буферах: USB, настройки и макросы
будут его перезаписывать. Проверенного свободного диапазона RAM на 480 байт
пока нет. Реализованный OL2 передаёт одну страницу прямо в нативный `draw-block`,
используя локальную копию пакета из 132 байт на стеке. Он не выделяет новых
глобальных переменных и не хранит sequence/ownership между командами.
Офлайн-проверка сохраняет stack canary; наблюдаемая глубина внутри расширения —
196 байт от входного SP. Реальные ROM/I²C вызовы могут увеличить глубину, а
допустимый запас стека физического устройства ещё не измерен.

Для устойчивой картинки нужен режим владения экраном. В текущем OL2 штатные
батарея/DPI/режим связи могут перерисовывать её. Требуется проверить и перехватить все штатные пути
отрисовки/выключения/пробуждения; одной записи четырёх страниц недостаточно.
Известные входы штатного рендера включают `0x3D51E`, `0x3D328`, `0x3D856`.
Полнота этого списка пока не доказана. Массово заменять низкоуровневые I²C
функции нельзя: новый uploader должен использовать те же примитивы.

## Выбор HID-канала

В HID report descriptor интерфейса конфигурации объявлен **report `0x22`
(34 десятичное)** с 131 байтом payload, то есть **132 байта вместе с ID**.
Это подтверждено исходными байтами `85 22 95 83 B1 01`.

В исследованном обычном приложении `SET 0x22` проходит общий обработчик
`0x33CD2` и попадает в default-return `0x33DFC`. Это также проверено исполнением
диспетчера в Unicorn. Для сравнения, `SET 0x10` достигает update-функции
`0x39446`; её исполнение в тесте останавливается до аппаратных действий.
ROM-helper switch в этом тесте заменён моделью обычной таблицы с ограниченным
индексом/default; сам код ROM не считан. Это ограничение офлайн-доказательства.

**Это не доказывает безопасность `0x22` в загрузчике.** Семейство объявленных
ID `0x22…0x2E` может принадлежать служебному/загрузочному протоколу; полный аудит
загрузчика и официального updater ещё не выполнен. Поэтому `0x22` ниже —
канал новой прошивки, а не разрешение посылать картинки штатной мыши. В OL2
HUB сначала читает **только штатный version report `0x0B`, 8 байт**, стандартным
проверенным A0/read-ready способом. Hook сохраняет исходную версию 1.08 и
добавляет маркер в три хвостовых нулевых байта:

```text
stock:  0B 05 01 01 08 00 00 00
OL2:    0B 05 01 01 08 4F 4C 32   // ASCII OL2
```

Хост должен проверить wired `VID_1D57&PID_2148`, длину, весь ожидаемый префикс,
версию и маркер. **Никаких GET `0x22` или пробных SET для обнаружения поддержки.**
Для stock-версии отсутствие OL2 отключает передачу. Беспроводной приёмник FA60
не является поддерживаемым каналом uploader.

## Реализованный ARM-протокол OL2

SET packet, ровно 132 байта:

| Offset | Length | Значение |
|---|---:|---|
| 0 | 1 | report id `22` |
| 1 | 1 | logical length `84` (=132) |
| 2 | 2 | magic ASCII `GO` |
| 4 | 1 | версия `02` |
| 5 | 1 | operation `01 WRITE_PAGE`; другие операции отклоняются |
| 6 | 1 | reserved, строго 0; sequence в OL2 нет |
| 7 | 1 | page 0..3 |
| 8 | 1 | payload length, строго 120 |
| 9 | 1 | flags 0 или 1; bit 0 вызывает штатный OLED_Init перед записью |
| 10 | 120 | байты страницы |
| 130 | 2 | CRC-16/CCITT-FALSE от bytes 0..129, little-endian |

CRC: polynomial `0x1021`, init `0xFFFF`, без отражения и финального XOR.
Он реализован настоящими Thumb-1 инструкциями, не ROM-stub. Этот CRC не связан
с проверочными словами контейнера прошивки.

До обращения к I²C ARM handler проверяет также transport length=132 и точный
штатный wired payload pointer `0x400F93`. Затем создаёт локальный snapshot
пакета на стеке и проверяет все поля, CRC и старшую тетраду каждой колонки
последней страницы. Неверный пакет возвращается без wake/init/draw вызовов.
Другие report ID вызывают исходный wake-handler, как до hook.

Каждая страница самодостаточна: можно обновлять их в любом порядке. Полный кадр
состоит из четырёх SET-пакетов. COMMIT, RESTORE, статус обработки, атомарный swap,
flash-сохранение и подавление штатной перерисовки **не реализованы**. Host должен
сериализовать передачи и выдерживать интервал обработки; успешный USB SET
сам по себе не доказывает завершённую отрисовку. Достаточный интервал и влияние
синхронной I²C-записи на задержку обычного ввода требуют физического измерения.

## Размещение кода и hooks

Сборка Clang 14, `--target=arm-none-eabi -march=armv5t -mthumb`, даёт `.text`
**280 байт без relocations**. ELF32 section/symbol table разбираются скриптом,
поэтому внешний ARM linker для этого исходника не нужен.

| Hook | Исходные 4 байта | Назначение |
|---|---|---|
| `0x33C94` | `11 70 40 78` | Replay `STRB r1,[r2] / LDRB r0,[r0,#1]`, добавить OL2 в padding version report |
| `0x33CD4` | `00 F0 10 FF` | Proxy вместо исходного `BL 0x34AF8`; только 22 попадает в uploader |

Каждый hook заменяется Thumb BL на соответствующий symbol в append-блоке.
Точные новые байты вычисляются по ELF symbols и сохраняются в
`bin/g9_oled-layout.json`; ожидать исходные байты обязательно.

Append начинается с VA **`0x47400`**, normalized offset **`0x1EC70`**, сразу за
3939 исходными valid CRC-блоками. 280 байт помещаются в 9 новых блоков по 32
данных + 2 checkword. Минимальный новый resource length — **134248** байт,
round-up до 4 KiB остаётся прежним **`0x21000` (135168)**. Используются исходные
198 байт FF-tail и часть округлённого padding; диапазон erase/write не расширяется.
В заголовке первых 16 байт пересчитываются CRC32 тела и длина в 4-байтных словах;
остальные десять байтов сохраняются. Прежнее требование неизменности всего
заголовка было ошибочным; см. [исправление](../docs/FIRMWARE-HEADER.md).
Эти расчёты не доказывают,
что bootloader примет увеличенный resource без физической проверки.

Скрипт builds только `.o`, `.text.bin`, layout JSON. Он не создаёт updater или
firmware resource. Builder отдельного кандидата должен заново проверить source
hash, все исходные CRC, hooks, новые CRC, FF-padding, CRC32 и длину header и
диапазона erase/write. Патч `0x3201C: 0D70→C046` для обычной «0» комбинируется
отдельно: loader layout не включает его автоматически.

Такой raw-resource builder реализован отдельно в
`tools/build_oled_candidate.py`. Он создаёт новый уникальный каталог внутри
`patch-output`, объединяет NOP + оба hooks + append, копирует неизменённые
исходные CRC-блоки побайтово и пересчитывает только три изменённых исходных
блока и девять добавленных. Результат заново декодируется; проверки ARM handler
и обычной «0» выполняются на **байтах фактического кандидата**, а не на другом
фикстурном образе. Рядом сохраняется manifest с hashes, изменениями и пределами.
Оригинал не перезаписывается, Update.exe не вызывается. Этот результат ещё
не означает допустимость физического обновления или возможность отката.

## Что будет работать при закрытом HUB

Это разные требования:

- **Обычная «0»** выполняется мышью; открытый HUB ей не нужен.
- **Статичная картинка** после передачи может оставаться в RAM самого OLED,
  пока он питается и прошивка не перерисовывает экран. OL2 не подавляет renderer и
  не обещает сохранение через сон, выключение питания или перезагрузку.
- **Картинка после пробуждения** требует хранения полного кадра в проверенной
  RAM MCU и его восстановления либо повторной передачи с ПК. Такой путь
  пока не реализован и сохранность RAM во всех режимах сна не подтверждена.
- **Картинка после выключения питания** требует отдельного проверенного
  flash-хранилища и загрузки при старте. Свободное место и безопасная схема
  сохранения ещё не установлены; существующие профили/макросы под это не
  переиспользуются.
- **Живые виджеты с данными ПК** (CPU, музыка, время ПК и подобное) требуют,
  чтобы HUB или его фоновая часть продолжали передавать обновления. Это
  обновление данных экрана, не перехват кнопки и не условие работы «0».

Reset/wake могут возвращать штатный экран; потеря HUB во время частичной
передачи оставляет частичную картинку до следующей штатной отрисовки. У OL2 нет
режима владения, который мог бы навсегда заблокировать native renderer.

## Воспроизведение

```powershell
wsl -e /mnt/d/repos/fxpw/test/FURYCUBE-G9-PRO/tools/pyenv/bin/python tools/emulate_oled_arm.py
```

Для создания только локального raw BIN-кандидата с проверкой, без USB:

```powershell
wsl -e /mnt/d/repos/fxpw/test/FURYCUBE-G9-PRO/tools/pyenv/bin/python tools/build_oled_candidate.py
```

Проверка компилирует настоящий handler и исполняет его с hooks в Unicorn,
читает stock/OL2 version reply, записывает четыре страницы через реальные
draw-block инструкции, проверяет отказ для 15 malformed/pointer/length случаев,
стек и legacy tail-call. ROM switch/zero-fill/memcpy, wake/profile restore,
OLED_Init и I²C hardware заменены эквивалентами/фиксацией аргументов. Новые CRC,
валидация и копирование snapshot не подменяются Python handler.

`tools/emulate_oled_protocol.py` — прежняя Python reference-модель v1 и отдельная
проверка native draw primitives. Она не является реализацией текущего OL2 API.

До применения к мыши остаются надёжный оригинальный образ и откат, независимая
проверка candidate builder, bootloader/update acceptance, геометрия контрольным
рисунком и физические проверки RAM/stack/I²C/input latency на поддерживаемой
ревизии. Ownership/wake/storage — последующая отдельная функциональность.
